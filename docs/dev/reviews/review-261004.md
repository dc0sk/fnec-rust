# Targeted audit for the FND-197/198 shape — 2026-10-04 (main fc17f25, v0.21.1)

The audit searched for siblings of FND-197 (a guard keyed on how an input is spelled in one source) and FND-198 (a step that assumes a shared matrix's state).

- **Finders:** four Opus finders, one per dimension: input-source guards, shared mutable state, frontend parity, and refusals placed above a dispatch on another axis.
- **Verifiers:** each finding was handed to its own verifier with a default verdict of *refuted*. A finding was kept only when the verifier re-ran it and reproduced it, usually against nec2c.
- **Synthesis:** done on a different model (Sonnet).
- **Result:** 14 candidates, 13 confirmed, 1 refuted.

The findings are recorded in the ledger as FND-199 to FND-211. Mapping from the audit's IDs:

## Executive summary

- 13 confirmed findings (14 candidates; F11 REFUTED: LOADS echoing LD cards is the documented contract, cli-guide:362). Every one was re-run adversarially.
- 10 of 13 are silent wrong answers (exit 0, no warning): F5, F8, F3, F1, F2, F6, F4, F9, F7, F13. The other three are a false refusal/warning (F10), a misleading remedy (F12) and a latent API contradiction (F14).
- Only 2 hit the DEFAULT path with no opt-in flag: F8 (gain ignores load loss in free space and PEC; CLI, GUI, py) and F3 (NE/NH near fields ignore ground; CLI).
- 8 need an opt-in flag: F1 (--solver mpie), F2 (--solver sinusoidal), F4 (--exec gpu), F5 (--hosts --exec gpu, or run_worker_stdio), F6/F7/F12 (--loads-config), F9/F13 (--ground-solver sommerfeld). F10 needs --sweep-config. F14 is latent.
- Worst: F5 (critical), a worker --exec gpu fallback solving on the raw grouping, |Z| 13x off with the reactance sign flipped on a 1+9+9+1 split.
- 1 critical, 6 high, 3 medium, 3 low. Largest measured errors: near-field Ex -91 % (F3), gain +3.37 dB (F8), impedance 5x (F7) and 13x |Z| (F5).
- Most are refusal/guard gaps with a documented "supported" claim in card-support-matrix or cli-guide; the fixes are mostly small refusals or one shared validation PR.

## Detail by area

### Solver choice (--solver)

**F1 (rank 4, high). MPIE drops the second voltage source.**
- Where: mpie_session.rs:160 `first_delta_gap_feedpoint` (excitation.rs:54 `.find`); `mpie_unsupported` (123-138) has no multi-source check. Frontends: CLI solve_session.rs:1054, GUI solve.rs:720/527, fnec_py lib.rs:108.
- Deck: two parallel dipoles, 3 m apart, EX on both. Hallén: 142.48+j25.73 on both; MPIE: 42.69+j77.76 and 15.73-j118.01; nec2c: 145.37+j34.69. Exit 0, no warning.
- Antiphase variant (found independently by the route-axis finder): nec2c 10.49-j27.57; MPIE 25.27-j46.01 / 10.38-j69.68.
- Docs claim the opposite: card-support-matrix:46 (EX 0 "Full" across all solvers incl. mpie), cli-guide:812 (multi-source supported).
- Fix: refuse MultipleSources in `mpie_unsupported` or superpose unit solves; correct the docs.

**F2 (rank 5, high, CLI only). `--solver sinusoidal` skips Hallén routing.**
- Where: solve_session.rs:1298-1342 (sinusoidal arm = merged_grouping + solve_hallen_sinusoidal_basis, fallback plain solve_hallen); loads-stamped paths None (1141-1147); refusals only for PEC contact (1160-1170) and TL/NT (1171ff). solver_ctx (678) gives sinusoidal `cli_hallen()`, so topology caveats are silent. The residual guard passes (1.63e-3, 8.10e-3 < 1e-2).
- split-V corpus: hallen 270.43+j443.20; mpie 245.05+j427.39; sinusoidal 10.27-j731.22; nec2c 268.56+j452.26.
- T deck: hallen 104.49-j379.90; sinusoidal 4.19-j1010.07; nec2c 107.54-j366.35. Exit 0, no warning.
- cli_args.rs:33 and warnings.rs:15 steer users to sinusoidal "for accurate results". GUI/py/worker do not expose it.
- A guard was removed: `sinusoidal_a4_topology_supported` (changelog 2890) no longer exists.
- Fix: refuse or fall back when the Hallén route leaves the plain basis, using the same routing predicate; add a CLI test vs nec2c.

### Execution / GPU / worker

**F5 (rank 1, CRITICAL). Worker `--exec gpu` on collinear splits solves on the raw grouping.** Found by 2 finders; severity upgraded after measurement.
- Where: nec_worker/src/solve.rs: raw `wire_endpoints_from_segs` (425) + `detect_wire_junctions` (504). The device declines deterministically (R=N+W+1 vs S=N+W, wgpu_device.rs:1800 "not square"), then `cpu_currents` (556/652) runs plain solve_hallen on the raw pairwise grouping with no FND-158 sin column. The decline reason is discarded, exec_used=cpu, no warning. The CLI uses merged_grouping (solve_session.rs:1222).
- 4-wire 1+9+9+1 split: exec cpu 76.678+j32.871; exec gpu 1032.215-j3723.820; nec2c 79.41+j45.63. 3+15+3 split: X off by 43 %.
- Split dipole fed 1/7: worker cpu 162.048+j66.258; worker gpu 161.047+j67.679. 3-wire chain: cpu 1046.22-j53.54; worker gpu 1046.34+j24.98 (78 ohm X); CLI gpu (device ran) 1046.21-j53.54; nec2c 1103.4+j35.1.
- Control: a single-wire deck on worker gpu runs on the device and matches. On this host the device declines every split deck, so the fallback always runs.
- Reach: `--hosts --exec gpu`, run_worker_stdio. The worker parity test only covers exec cpu.
- Fix: merged_grouping in the worker GPU arm; fallback goes through solve_hallen_routed; add parity test exec gpu vs cpu on a split deck.

**F4 (rank 7, high). `--exec gpu` radiation pattern ignores ground.**
- Where: solve_session.rs:1438-1471, Gpu arm calls `run_rp_farfield_batch_wgpu` (no ground; only total_radiated sees pec_ground, 1442-1443). The CPU arm (~1496) and the no-adapter fallback pass ground.
- GN 1 vertical dipole: cpu/hybrid -3.12/-0.26/-15.04 dBi (= nec2c); gpu -8.62/-2.56/+0.67. GN 2: cpu -5.06/-1.59/-2.94 (= nec2c); gpu -13.68/-7.63/-4.40. Exit 0, no warning. Diag shows the solve fell back to CPU while RP ran on GPU.
- GE 0 control: cpu == gpu (kernel fine). Sweeps: every point wrong. Not affected: hybrid, auto, GUI, worker, py.
- Docs cli-guide 570-573 carry no ground caveat.
- Fix: GPU RP only for FreeSpace, else CPU compute_radiation_pattern; gate GN 1 RP gpu vs cpu.

### Outputs: pattern / near-field / gain

**F8 (rank 2, high, default path). Gain ignores load loss in free space and over PEC.**
- Where: farfield.rs:317 `gain_correction_db` returns None unless SimpleFiniteGround (comment 307-309 "lossless"); CLI gate solve_session.rs:1519 (comment 1514-1518). The finite path's eta = P_rad/P_in (farfield.rs:381-395) already includes load loss. Shared producer: CLI, GUI, py.
- Lambda/2 dipole at 299.79 MHz, LD 4 100 ohm at the feed: free space fnec 2.1724 vs nec2c -1.20 dBi (eta 45.89 %), 3.37 dB high = -10log10(eta). PEC: fnec 6.4047 vs 3.01.
- Controls: unloaded 2.17/2.18 and 6.40/6.40 match; GN 2 loaded -0.78 vs -0.73 OK. Exit 0, no warning.
- Docs call the column "gain" (cli-guide 329, card-support-matrix 123).
- Likely sibling, not run: RP A-digit AVERAGE_POWER_GAIN reading about 1 for loaded free-space decks.
- Fix: apply eta = P_rad/P_in for every ground (integrate_power_for_ground handles free/PEC); gate loaded free/PEC decks vs nec2c efficiency.

**F3 (rank 3, high, default path, CLI only). NE/NH near fields ignore the ground.**
- Where: farfield.rs:154 `near_e_field` and ~218 `near_h_field` take no ground; rows built at solve_session.rs:480/520, called 1554-1555 (ground is in scope there and is passed to gain_correction_db just above). Free space is within 4 % of nec2c. GUI/py compute no near fields.
- GN 1 vertical dipole, z 5-15, points at x=30: Ez at z=1 0.02129 vs 0.04304 (-51 %); z=5 -40 %; z=9 -20 %; Ex at z=9 -91 %; (30,0,40) Ex -16 %; Hy at z=1 -51 %. GN 2: Ez at z=5 -10 %; Ex at z=9 -81 %. PEC monopole (contact) at (30,0,3): Ez -50 %, Ex -80 % (missing image half). Exit 0, no warning.
- Docs (card-support-matrix 86-87, cli-guide 766) caveat only near-the-wire.
- Fix: image sum (PEC sign; Fresnel-scaled for GN 0/2 like the far field), or refuse/warn on NE/NH over ground until then; fix docs.

### Ground: Sommerfeld (--ground-solver sommerfeld)

**F9 (rank 8, medium). dZ on multi-feed / broadside-parallel decks.** Two mechanisms.
- (1) sommerfeld.rs:165-175 (+ general path) computes <J_tot, dG J_tot>/I_p^2, and build_feedpoint_rows (solve_session.rs:854-867) gives each port the whole-structure reaction. The correct form is <J_p, dG J_tot>/I_p (identical for one port). For a symmetric pair the code gives 2(dZ11 +/- dZ12).
- (2) `horizontal_ground_z_correction` uses the along-axis scalar kernel `reflected_ex_horizontal(|rho|)` (sommerfeld.rs:355-357) for broadside offsets (gate at 113-126 checks only parallel + same height), missing the cos 2phi sign of the J2 term.
- Side pair, GN 2, h=2 m, 5 m apart, +/+: nec2c 75.01-j30.15; rcm 65.39-j33.57 (warns); somm 76.29-j65.29 (no warning). +/-: nec2c 27.11-j17.86; somm 44.79-j3.25. Collinear controls: halving delta leaves the lone-wire residual.
- When applied, it suppresses the low-ground caveat (solve_session.rs:1405-1411). Docs claim "any straight wire" (card-support-matrix 24/26, cli-guide 41).
- Fix: decline with the existing Declined warning for >1 feedpoint and for off-axis parallel wires (or per-port unit solves + dyadic kernel).

**F13 (rank 10, medium). dZ uses network-augmented feed currents.**
- Where: solve_session.rs:1374-1377 `feed_i_vec` (includes the network branch current) feeds build_feedpoint_rows then ground_z_correction (854-866; sommerfeld.rs:175/224).
- Dipole at z=1.5, GN 2, far stub, NT shunt -j0.01 S: antenna currents unchanged; rcm and nec2c obey the exact parallel relation. Sommerfeld 26.068+j40.557 vs consistent 24.142+j41.338 (R +8 %). Exit 0.
- Fix: pass antenna i_vec; apply dZ to Z_ant, then parallel the network.
- F9 vs F13: both reach ground_z_correction via build_feedpoint_rows but the mechanisms differ (port reaction form and kernel vs which current vector is passed); one fix does not cover both, so they stay separate.

### Inputs: loads-config / sweep-config

**F6 (rank 6, high; FND-161 sibling). A `--loads-config` entry matching no segment is silently dropped.**
- Where: loads.rs:294-307 `laplace_segment_matches` matches nothing; `add_laplace_loads` (313-345) warns only on empty/non-finite coefficients.
- 21-seg dipole at 28 MHz: unloaded 62.9679-j54.3765; correct load 162.9679-j54.3765. tag=9, seg_first=11 seg_last=5, tag=-1 (u32 wrap) and seg_first=99 all give exactly the unloaded value, exit 0, nothing on stderr. The equivalent `LD 4 9 11 11 100 0` exits 1 with "names no segment".
- Fix: validate each LaplaceLoad like ld_card_problem (zero match, reversed, negative/non-integer) with a pre-solve refusal.

**F7 (rank 9, medium). Parser turns unknown/missing keys into 0 (=all).**
- Where: laplace_config.rs:41 `get_u32` uses `unwrap_or(0) as u32`; :36 a missing table gives Ok(empty); unknown keys are never rejected.
- `segment = 11` (wrong key): 866.41-j431.27 vs 162.97-j54.38 (5x). `[[laplace_loads]]` (misspelled table): unloaded, and bypasses the MPIE refusal (mpie exit 0, unloaded 65.05-j47.75, vs exit 1 when spelled right). tag=1.0: both wires loaded (144.43-j62.84 vs 132.68-j83.77).
- Explicit 0 = all is documented (cli-guide 68-70), so that part is intended.
- Fix: serde deny_unknown_fields, integer types, required seg_first, reject files with no loads or other top-level keys. F6 + F7 = one PR ("validate the loads file").

**F12 (rank 11, low). Negative-R caveat recommends `--solver mpie`, which refuses `--loads-config`.**
- Where: validate.rs:660 `negative_resistance_cause` remedy via `mpie_compatible_deck(deck)`, which looks at cards only.
- Laplace -200 ohm: Z -121.59+j42.77 (correct), but the warning says re-run with mpie, which exits 1 with a refusal. The LD twin gets a different remedy. The cause text is also wrong (it is the user's negative load).
- Fix: pass the resolved loads to the remedy choice; name a negative load as the cause.

**F10 (rank 12, low, no wrong answer). `--sweep-config`: deck FR still drives a refusal and a warning.**
- Where: validate.rs:1511-1521 `frequency_error` / `network_card_error` use the deck FR (833, 1559); main.rs:301 `superseded_frequency_warnings` runs before the sweep config is read (370-380).
- FR -14.2 + sweep [14.2]: exit 1, false refusal. FR 7 + FR 14 + sweep [14.2]: warns "runs at 14 MHz" but solves 14.2. Networks are rebuilt per frequency and fail loudly.
- Context: FND-151 (rejected) made deck-FR checking deliberate, but cli-guide:51 says the sweep config REPLACES FR.
- Fix: skip deck-FR checks/warnings when `--sweep-config` is given; check networks at the resolved frequencies.

### API

**F14 (rank 13, low, latent). `pub solve_current_source_hallen` has a contradictory matrix contract.**
- Where: current_source.rs:83 rustdoc says "includes stamps"; the plain/path arms read caller stamps; the graph arm (157-163) wants an unstamped matrix and rebuilds deck loads (dropping Laplace). Re-exported at lib.rs:29. The only non-test caller, hallen_session.rs:1701, never reaches the graph arm.
- Fix: take the load diagonal and an unstamped matrix and own stamping (as PlaneWavePlan does), or make it pub(crate) and fix the doc.

## The pattern

Classification is mine, based on the verdict text. About 8 of 13 are the FND-197 shape, a guard or decision keyed on one axis or source while the dispatch consumes another: F1 (the MPIE guard knows cards, not multiple sources), F2 (the sinusoidal arm skips the routing and the removed topology guard), F4 (the solve's GPU guard keys on deck class, the RP arm on the exec flag alone), F5 (CLI uses merged_grouping, worker raw: an "N copies, one diverged" variant, with the decline reason discarded), F6 and F7 (loads-file entries are not validated like LD cards; the misspelled table also bypasses the MPIE refusal), F10 (deck FR keys checks that sweep-config replaces), F12 (remedy keyed on cards only, not resolved loads). Two are the FND-198 shape, state assumed: F13 (a consumer takes feed currents that are network-augmented and assumes antenna-only) and F14 (a pub function with contradictory stamped/unstamped expectations, explicitly the same matrix contract that FND-198 broke). Three are neither: F3 (ground never plumbed into the near-field function), F8 (gain assumes a lossless structure; the "lossless" comment predates loads over free/PEC) and F9 (wrong reaction formula and kernel, a math gap rather than a guard gap). Of the ten silent wrong answers, the F197-shape ones account for six (F1, F2, F4, F5, F6, F7). The common root is again "one input resolved in one place and spelled differently in another". All of the FND-197-shape findings sit behind an opt-in flag or config file, which is why the default path stayed clean for them; the two default-path findings (F3, F8) are the "other" kind.
