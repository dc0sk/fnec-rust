# Project Review — 2026-07-19

## Scope and method

Full multi-agent audit of the fnec-rust workspace covering seven dimensions:
stubs/dead-code, panics-in-libs, seam-gaps (cross-frontend parity), test-coverage
gaps, domain-logic correctness, documentation drift, and concurrency hazards.

7 finder agents ran in parallel, each producing up to 7 findings.  Each finding
was adversarially verified by a separate agent (default REFUTED; only confirmed
or uncertain kept).  This report contains the deduplicated, severity-ranked
survivors.

**Codebase snapshot**: v0.12.0, 7 workspace crates, 2 apps (CLI + GUI),
1 Python binding crate (excluded from workspace build).

---

shipped them), and the Notes bullets still described GPU acceleration as

existing prose: `--hosts` has no local fallback (a missing file or unreachable
worker exits 1), and `--ground-solver sommerfeld` applies to any straight wire —
not only a horizontal one — while declining bent geometry silently.

## Executive summary

The codebase is **structurally solid for a scientific-computing library of this
age**: no unsafe blocks in library crates, no data races in the CPU path, and a
well-tested solver core.  The three systemic issues are:

1. **Documentation drift** — the CLI guide is stuck at v0.2.0-era content while
   the codebase is at v0.12.0.  Six features that shipped months ago are still
   described as stubs or deferred in the primary user-facing doc.
2. **Cross-frontend parity** — the GUI and Python bindings bypass geometry
   validation, solver-mode selection, and diagnostic warnings that the CLI
   enforces.  Users on non-CLI frontends silently get wrong results for
   degenerate decks.
3. **GPU resource management** — every wgpu kernel call re-creates
   Instance+Adapter+Device from scratch (no caching), and `device.poll().unwrap()`
   panics on GPU loss instead of falling back to CPU.

The most actionable single fix is updating `docs/cli-guide.md`, which is
approximately 10 minor versions behind the code.

## Top findings (ranked by severity × blast-radius)

### FIND-001 [HIGH] `--ex3-i4-mode` documented as active but silently ignored

**File**: `apps/nec-cli/src/cli_args.rs:121-123`, `docs/cli-guide.md:42`
**Verdict**: confirmed

The CLI guide describes `--ex3-i4-mode` with two behavioral semantics ("legacy"
and "divide-by-i4").  The flag is accepted but is a silent no-op:
`// flag removed in phase-1 simplification — silently ignore for backward
compat`.  `ex_cards.rs:293` explicitly calls it "an obsolete no-op".  Users
following the guide believe the flag has an effect it does not.

**Fix**: Remove the option from the guide, or remove the flag from the CLI
entirely with an error message for backward-incompatible break.

---

### FIND-002 [HIGH] CLI guide missing three shipped features

**File**: `docs/cli-guide.md:18,35-46`
**Verdict**: confirmed

The synopsis and Options table omit `--ground-solver` (Sommerfeld ground,
shipped 0.7.0), `--hosts` (distributed SSH execution, shipped 0.11.0), and
`--output-format` (JSON output, shipped 0.10.0).  These are non-trivial features
invisible to anyone reading the guide.

**Fix**: Add all three to the synopsis and options table with descriptions.

### FIND-004 [HIGH] Python bindings have separate solve path with zero validation

**File**: `bindings/fnec_py/src/lib.rs:47-115`
**Verdict**: confirmed

`fnec_py.solve_at_freq()` performs: build_geometry → build_excitation →
solve_hallen → feedpoint Z.  No geometry validation (intersection/source-risk/
buried-wire), no DeckValidator, no topology warnings, no load/TL warnings,
no report output.  Returns a bare dict with Z_re/Z_im.

**Fix**: Extract the validation pipeline from CLI into `nec_project` or a shared
crate and call it from all three frontends.

---

### FIND-005 [HIGH] Each wgpu kernel invocation re-creates Instance+Adapter+Device

**File**: `crates/nec_accel/src/wgpu_device.rs:843,1371`
**Verdict**: confirmed

Every GPU entry point (`fill_zmatrix_wgpu`, `solve_hallen_gpu_resident`,
`run_rp_farfield_wgpu`) independently calls `wgpu::Instance::new` +
`request_adapter` + `request_device`.  No `OnceLock`/`OnceCell`/lazy caching
exists.  Under `--exec gpu` with N frequency points, this creates O(N) redundant
device-init calls.

**Fix**: Cache the wgpu Instance+Adapter+Device in a `Lazy<OnceLock<...>>` or
module-level static and reuse across calls.

### FIND-006 [MEDIUM] GUI skips all geometry validation

**File**: `apps/nec-gui/src/solve.rs:314-373`
**Verdict**: confirmed

CLI `main.rs:264-288` calls `segment_intersection_error()`,
`source_risk_geometry_error()`, and `buried_wire_geometry_error()` as hard
errors before solving.  GUI `solve_deck_str()` goes straight from
`build_geometry` → `solve_hallen` with zero validation calls.

**Fix**: Call the same validation functions in the GUI solve path.

### FIND-007 [MEDIUM] GUI omits junction/topology diagnostic warnings

**File**: `apps/nec-gui/src/solve.rs:277-312`
**Verdict**: confirmed

GUI's `collect_solve_warnings()` checks `classify_unsupported_topology` but
omits `warn_if_feedpoint_at_junction()`, `warn_if_low_finite_ground()`, and
`warn_ge_ground_reflection_flag()` — all present in CLI `solve_session.rs`.

**Fix**: Call the same warning functions and surface them in the GUI.

---

### FIND-008 [MEDIUM] GUI has no solver-mode selection — hardcoded to Hallen

**File**: `apps/nec-gui/src/solve.rs:355`
**Verdict**: confirmed

GUI always calls `solve_hallen`.  CLI supports `--solver`
(hallen|pulse|continuity|sinusoidal|mpie), `--ground-solver`, `--exec`,
and `--pulse-rhs`.  Decks requiring MPIE (junctions, loops) silently produce
unreliable Hallen results.

**Fix**: Add solver-mode selection UI or at minimum warn when
`classify_unsupported_topology` indicates a non-Hallen solver is needed.

---

### FIND-009 [MEDIUM] WorkerPool dispatch is serial (`&mut self`)

**File**: `crates/nec_worker/src/pool.rs:138`
**Verdict**: confirmed

`WorkerPool::dispatch` takes `&mut self`, preventing concurrent task
submission to multiple workers.  For M frequency points across N SSH workers,
total wall time is O(M × latency) instead of O(M/N × latency).

**Fix**: Redesign dispatch to `&self` with concurrent submission per worker.

---

### FIND-010 [MEDIUM] `device.poll().unwrap()` panics on GPU loss

**File**: `crates/nec_accel/src/wgpu_device.rs:1034`
**Verdict**: confirmed

`device.poll(PollType::Wait{..}).unwrap()` — if the GPU device is lost
(timeout, driver crash), `poll()` returns `Err` and the unwrap panics.
Under rayon parallelism this aborts the entire frequency sweep with no CPU
fallback.

**Fix**: Replace `.unwrap()` with error handling that returns `None` (triggering
the CPU fallback path already present for adapter/device-request failures).

---

### FIND-011 [MEDIUM] `nec_project` crate is entirely unwired

**File**: `crates/nec_project/src/lib.rs`
**Verdict**: confirmed

nec-cli lists `nec_project` as a dependency but never imports it.  The entire
public API (`ProjectFile`, `SolverConfig`, `NamedRun`, `RunHistory`) is consumed
only by the crate's own tests.  619 lines of serialisation, markdown round-trip,
and run-history API that no production code uses.

**Fix**: Either wire it into the CLI/GUI (replacing ad-hoc project handling) or
remove it from the workspace until needed.

---

### FIND-012 [MEDIUM] `Card::Nh` reuses `NeCard` struct — domain model confusion

**File**: `crates/nec_model/src/card.rs:414`
**Verdict**: confirmed

`enum Card` has `Nh(NeCard)` reusing the `NeCard` struct documented as
"NE — Near electric-field request card".  NH in NEC-2 is the near-**magnetic**
field card.  A `NeCard` populated from an NH card has field semantics that don't
match the struct's documented meaning.  Three production files construct
`Card::Nh(card)`.

**Fix**: Rename `NeCard` to `NearFieldCard` or create separate types.

## Refuted findings (not bugs)

| Claim | Reason for refutation |
|:------|:----------------------|
| Pocklington off-diagonal Green's function wrong | Bare distance R is correct for Pocklington; reduced kernel r_eff is Hallén-specific |
| Multi-source Hallén RHS axis projection wrong | Bent junctions correctly routed to path-aware `build_hallen_rhs_paths` |
| `parse_u32` truncating cast is a panic | f64→u32 saturates silently; defined Rust behavior, not a panic |
| `unwrap()` on `rx.recv()` in GPU path | Unreachable after successful `device.poll()` |
| `unwrap()` on `ordered_segs` in conductor walk | Walk guarantees ≥1 segment by construction |
| `unwrap()` on `max_by()` in LU pivot | Range `col..n` always non-empty when `col < n` |
| `expect()` on stdin/stdout pipe take | Unreachable — `Stdio::piped()` guarantees `Some` |
| GUI swallows load/TL warnings | Warnings re-collected via `collect_solve_warnings()` |
| `worker.rs` never tested with valid task | Integration tests in `worker_integration.rs` cover this |
| `template.rs` only 4 tests | Has 7 unit tests + 5 integration tests |
| `controller.rs` dispatch never tested | Integration tests exercise it |
| `ReportSection` has zero consumers | `render_text_report_with_sections` is the consumer |
| `DispatchDecision::RunOnGpu` never constructed | Intentionally reserved for future GPU dispatch |
| `pollster::block_on` from rayon threads | GPU path not reached from rayon (hybrid mode uses CPU indices) |
