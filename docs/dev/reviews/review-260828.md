# Whole-project audit — 2026-08-28/29 (post-v0.17.0, main = 25fb641)

Scope: a 10-dimension parallel audit of `fnec-rust`'s four frontends (`fnec`
CLI, `fnec-gui`, `fnec_py` PyO3 bindings, `fnec worker --stdio`) and two
solvers (Hallén default, MPIE `--solver mpie`), run immediately after the
v0.17.0 release with the findings ledger at **zero open items**. Every finding
below is therefore previously unrecorded.

## 1. Executive summary

A user of this software can get real, silent wrong answers today, not just
missing features:

- **Any deck that uses `LD`, `TL`, `NT`, or `--loads-config`** solves to
  quantitatively wrong currents and feedpoint impedance on **all four
  frontends**, with no warning (R56). A 100 Ω load at the feed inflates Z by
  ~7×; off-feed series loads can make R go the wrong direction entirely. The
  in-tree regression fixture for this exact case has had its tolerance
  widened to 6500 Ω specifically so the 6.6× disagreement with an external
  oracle stays green.
- **Any bent or split geometry that the CLI solves correctly** (inverted-V,
  L-shapes, T/Y junctions, common ham antennas) is answered with a **wrong
  impedance** by the GUI, `fnec_py`, and the worker — measured 29× wrong in R
  with the reactance sign flipped on the worker — because the shared
  junction/paths caveat is structurally suppressed for exactly the geometry
  class that solves wrongly (R43).
- Real-world **`GM`-card decks** (stacked arrays, elevated copies) silently
  lose wires because field 2 is parsed as "last tag" instead of NEC-2's NRPT
  (R57). **Two `EX` cards on one wire tag** silently drop the second source
  while still reporting it as driven (R58). **`EX 4` current-source decks over
  ground** get a materially different impedance depending which of two
  internal formulations runs, with no caveat, on all four frontends (R50).
- A **distributed run** (`--hosts`) of any deck whose feedpoint goes to
  negative or infinite resistance at one swept point — which the project's
  own corpus ships as fixtures — **kills the entire worker pool** (R44), and a
  crafted `GR`/`GM` replication count **panics the worker process** or aborts
  the Python host outright (R08).
- Below that: a long tail of unbounded-allocation crashes on untrusted deck
  input (RP/NE grids, sweep-config, worker stdin), CI/local gates that pass
  for the wrong reason (a benchmark gate read through a pipe, a findings-
  ledger checker with a literal-match bypass), and docs/roadmap pages that
  describe capabilities or trackers that no longer match the code.

Nothing here was hidden by complexity — most of these are one deck, one
command, no special flags.

## 2. Method and its limits

- 10 parallel finder agents, one per audit dimension, produced 62 raw
  findings; 3 exact cross-finder duplicates were merged to **59 distinct
  claims**.
- Each of the 59 went through one adversarial verifier, default verdict
  REFUTED — the verifier had to reproduce or directly re-read the mechanism
  to confirm.
- One further finding, **R63**, was discovered *by a verifier* while checking
  another claim (R46), and was itself put through a verifier — bringing the
  total to **60 verified**.
- Outcome: **59 confirmed, 1 refuted (R49)**. **21 findings were downgraded in
  severity on verification; none were upgraded.** Final severity mix: **2
  critical, 8 high, 30 medium, 19 low.**
- The finders were reliable about *mechanism* — which line does what, and how
  to reproduce it — and systematically inflated *blast radius*: how many
  frontends/decks/configurations are actually hit. Three examples where the
  verifier's own measurement corrected the finder's scope claim, not just its
  wording:
  - **R24** (GUI skips the gain correction on current-source decks): the
    finder's headline number was "6.04 dB" divergence, quoted from a
    different (FND-053) case; the verifier recomputed against the actual
    CLI reference for this deck and got **~5.78 dB**, not 6.04.
  - **R08** (u32 tag overflow): the finder's impact text said the same
    overflow "aborts the host Python interpreter" via `fnec_py`; the verifier
    checked and PyO3 0.23 raises a catchable `PanicException` instead of
    aborting — a real but smaller failure mode than claimed for that one
    frontend.
  - **R59** (TL card layout): the finder's core claim was two-part — "fnec
    misparses a standard NEC TL card" *and* "fnec's series-Z insertion is the
    wrong physics vs NEC's shunt network." The verifier proved the first part
    and found it was **worse** than stated (a valid deck with nonzero shunt
    admittances is silently accepted and answered with different physics, no
    warning at all) — but explicitly marked the second part **not
    established**: the near-open two-port probe used to test it moved the
    feedpoint by a magnitude inconsistent with a pure shunt insertion, but the
    comparison is confounded because the two baselines already differ. That
    sub-claim is reported here as uncertain, not smoothed into the finding.
- 21 of 59 were downgraded, concentrated in two shapes: (a) a finder graded
  severity from a deck-input class ("any RP card crashes the CLI") without
  checking which of the four frontends the code path actually reaches — e.g.
  R18's RP-grid allocation crash was filed `critical` and downgraded to
  `medium` once the verifier confirmed it is CLI-only (the GUI uses a
  compile-time-fixed grid; worker/bindings never reach `FarFieldPoint` at
  all); and (b) a finder treated a documented, already-tracked design
  decision as an undiscovered defect — e.g. R62's buried-wire refusal
  (PH2-CHK-002, with its own locked regression case) and R60's negative-R
  pulse-mode output (a documented deliberate exclusion, not a missing guard).

## 3. Ranked findings

Ranked severity × blast-radius, confirmed findings only (all 59 survived);
within a tier, broader/no-escape-hatch findings are listed first.

### Critical

**R56 — Load stamps (ohms) added directly to the dimensionless Hallén
A-matrix; every loaded deck is wrong on all four frontends.**
`crates/nec_solver/src/stamps.rs:57`, `matrix.rs:131`; applied at
`apps/nec-cli/src/solve_session.rs:1114`, `crates/nec_worker/src/solve.rs:429`,
`apps/nec-gui/src/solve.rs:500`, `bindings/fnec_py/src/lib.rs:104`.
Port-identity measurement: 100 Ω at the feed gives fnec `+699.86+j134.76`
against an expected `179.35+j46.223` (nec2c-anchored); the over-application is
a clean linear **7.0×** (0.1 Ω → +0.700, 1 Ω → +6.999, 10 Ω → +69.99). Off-feed
50 Ω series resistors move R the *wrong direction* (`-2.29-j0.39` vs nec2c's
`+70.8`). No warning fires on any run, and `corpus/reference-results.json`'s
`dipole-ld-loaded-51seg` case has its `ExternalR_absolute_ohm` tolerance
widened to 6500.0 with a status note admitting the disagreement, rather than
failing. **Fix sketch:** convert the load stamp to the same units as the
matrix entries (or convert the matrix to ohms) before `add_to_diagonal`;
un-widen the corpus tolerance once the gate can actually fail on this case.

**R43 — Bent/split-geometry Hallén solve is CLI-only; GUI/`fnec_py`/worker
silently answer it wrong, and the shared junction caveat is suppressed for
exactly that class.**
`apps/nec-cli/src/solve_session.rs:1148` (paths branch, CLI-only);
`crates/nec_solver/src/validate.rs:453` (suppression);
`apps/nec-gui/src/solve.rs:539`; `bindings/fnec_py/src/lib.rs:137`;
`crates/nec_worker/src/solve.rs:558`. Measured on one deck/frequency: CLI
`264.882+j410.856`, worker `9.152-j767.601` (29× wrong in R, reactance sign
flipped), nec2c oracle `268.56+j452.26`. Both warning producers consumed by
the other three frontends call `feedpoint_at_junction_warnings`, and
`classify_unsupported_topology` returns `None` whenever `build_conductor_paths`
is `Some` — every caveat channel is closed for exactly the geometry solved
wrongly, and R stays positive so the negative-R tripwire doesn't fire either.
No non-default config needed; Hallén is the default solver and bent/split
geometry (inverted-V, L, T) is common. **Fix sketch:** route GUI/`fnec_py`/
worker through the same paths-aware solve entry point the CLI already has,
and add a cross-frontend parity test on a bent/split deck.

### High

**R57 — `GM` card field 2 parsed as "last tag" where NEC-2 defines it as
NRPT (repeat count); standard multi-wire replication decks silently lose
wires.** `crates/nec_parser/src/lib.rs:143-157`,
`crates/nec_solver/src/geometry.rs:765`, `crates/nec_model/src/card.rs:351-373`.
A two-`GW` deck plus one `GM`: nec2c produces 44 segments (tags 1/2/11/12),
fnec produces 33 (tags 1/2/11) — wire 2 is silently not copied. NRPT≥2 is
unrepresentable at all. The verifier also found the codebase's `ITGI==0 ⇒
move in place` special case is *itself* non-NEC — NEC keys that behavior off
`NRPT==0`, not `ITGI==0` — confirmed against a second corpus fixture that
already diverges from nec2c (102 vs 51 segments) for this reason. **Fix
sketch:** parse field 2 as NRPT and gate the in-place special case on
`NRPT==0`.

**R50 — Current-source (`EX 4`) and voltage (`EX 0`) drives report different
impedances for the same antenna over ground; every `EX 4` corpus fixture is
free-space, so the class is ungated.** `crates/nec_solver/src/current_source.rs:89`.
The `EX 4` RHS synthesizes its drive through the free-space Hallén basis and
least-squares-solves against the ground-modified matrix, which stops fitting
once the ground image kernel enters; the disagreement is height-dependent,
roughly 2–14%, and shows up even at 0.24λ where no warning fires at all (GN1
emits none; GN2 emits only the generic sub-0.1λ warning shared with `EX 0`).
This directly violates the project's own stated internal-consistency gate
("V/i0 equals the voltage-source feedpoint impedance"), which every in-tree
test satisfies only because every `EX 4` fixture is free-space. MPIE is not a
clean tie-breaker (R lands near the `EX 0` path but X is 44.66 vs 13.62) and
also refuses `EX 4` outright. **Fix sketch:** derive the `EX 4` RHS against
the ground-modified basis directly, or caveat `EX 4` over any non-free-space
ground the same way other ground limitations are caveated.

**R58 — A second delta-gap source on the same wire tag is silently dropped;
a symmetric two-source dipole solves asymmetrically while both sources are
reported as driven.** `crates/nec_solver/src/excitation.rs:215-231`
(`source_by_tag` keyed by tag, `if ex2.tag == driven_tag { continue; }`).
Decisive ablation: deleting the second `EX` card produces a `CURRENTS` block
byte-identical to the two-source run — the second source contributes exactly
nothing — while the report still prints `N_SOURCES 2` and a feedpoint row for
it derived from a current that source never drove. All three corpus
multi-source decks happen to use different tags, so this is entirely ungated.
**Fix sketch:** key source lookup/dedup by (tag, segment) or EX-card index,
not tag alone.

**R44 — Infinite VSWR serializes as JSON `null` on the worker wire, which the
controller cannot parse; one negative-R or purely-reactive point evicts every
worker in the pool.** `crates/nec_worker/src/worker.rs:187-198`,
`protocol.rs:284`, `ssh_worker.rs:167`, `controller.rs:66`, `pool.rs:225-232`.
Reproduced on the corpus's own `inverted-v-negative-r-freesp.nec`: worker
emits `vswr_50:null`, serde returns `Err` on both transports, and `pool.rs`
loops evicting every erroring worker until "all workers in pool failed" —
while the local CLI solves the identical deck and prints Z with a caveat.
Aggravating factor: `main.rs:339` refuses `--solver mpie` with `--hosts`, so
the junctioned decks most likely to hit this are forced onto the failing
path. **Fix sketch:** serialize `vswr_50` as an explicit tri-state (finite /
+∞ / undefined), not a bare `f64`, and stop treating a domain-valid
non-finite result as a dispatch error.

**R24 — GUI silently skips the lossy-ground gain correction on
current-source decks because `feedpoint_input_power` reads an all-zero
excitation vector.** `crates/nec_solver/src/farfield.rs:334`. `apply_ex`
early-returns for `CurrentSource`/`PlaneWave` without writing `v`, so
`p_in = 0.0` exactly, `gain_correction_db` returns `None`, and the GUI
`unwrap_or(0.0)`s it — recreating the FND-053 divergence on the newest
current-source-solving path (#413) between the CLI (correct) and GUI
(uncorrected). The fix already exists on this path: `solve_currents` returns
`Some(fp.port_voltage)` and it's discarded at `solve.rs:1072`
(`let (currents, _port_voltage)`). **Fix sketch:** stop discarding
`port_voltage` there and feed it to `gain_correction_db` as the CLI does.

**R29 — Boolean phase guards can't tell which in-flight request a completion
belongs to; a superseded solve/sweep can win and the correct result is
dropped.** `apps/nec-gui/src/app_state.rs:498-560`, `main.rs:1118`.
`awaiting_solve`/`awaiting_sweep` are kind-of-run booleans with no run
identity and no cancellation anywhere in `nec-gui`. Traced concretely on the
sweep leg: a stale run's next point seeds the accumulator with an old
solver's point, both streams append into one vector, and the stale run's
`SweepStreamDone` finalizes the mixture as `Done` — a chart mixing two
solvers' points at duplicate frequencies, presented as the answer. **Fix
sketch:** give every solve/sweep request a monotonic run id; guard every
completion arm on id match; add real cancellation.

**R30 — All three 3-D viewport completion arms are completely unguarded;
stale solves repopulate the viewport after the state that launched them is
gone.** `apps/nec-gui/src/app_state.rs:605-659` (cf. discard at 938-956).
`ViewportState` has no phase enum and no run id; `discard_solver_derived_state`
clears exactly the fields these three arms unconditionally rewrite, and the
solver is captured at spawn time so a completion genuinely carries another
solver's numbers while the solver picker sits visibly unlocked beside it.
Display-only (no persisted wrong result), but it silently undoes a
deliberate guard and switches on overlays the user never touched. **Fix
sketch:** add the same run-id guard used for the four tabbed pipelines to the
viewport's three completion arms.

**R08 — u32 tag-arithmetic overflow in `GR`/`GM` geometry replication panics
(debug) or silently corrupts tags (release).** `crates/nec_solver/src/geometry.rs:809`
(`seg.tag += gr.tag_increment * copy_idx`, unchecked `u32`). Reproduced: a
6-line deck kills `fnec worker --stdio` outright (exit 101, no JSON line, no
`catch_unwind` anywhere in the tree); no `[profile]` section in any
`Cargo.toml` means release builds wrap silently rather than panicking. In
`fnec_py`, PyO3 0.23 raises a catchable `PanicException` rather than aborting
the host interpreter (correcting the finder's stronger claim). **Fix
sketch:** use checked/saturating arithmetic (or widen to `u64`) for the tag
computation and refuse a deck that would overflow.

## 4. Cross-cutting themes

**(a) The corpus is a regression gate presented as an external-validation
gate — confirmed, and it is exactly what let both criticals survive to a
release.** `corpus/README.md:10` claims every deck is "validated against
[a] reference engine (primary: xnec2c...)"; the recorded `reference_engine`
field for the load-stamp fixture reads "fnec Hallén solver (regression)" and
only 8 of 48 cases carry an `external_reference_candidate`, explicitly marked
pending (R53). R56's own fixture shows the mechanism in action: the tolerance
on the one case that *does* carry an external candidate was widened to 6500 Ω
specifically to keep it green against a 6.6× disagreement. R50's EX-4 gate
and R59's TL/NT equivalence test are both self-consistent checkers by the
same shape — the EX-4 internal-consistency assertion is never tested against
a ground fixture, and the TL/NT test compares two builders that stamp the
identical pattern into the same matrix, so it cannot detect a wrong insertion
model. Four independent findings, one mechanism.

**(b) "N copies, one diverged" recurs across solver, frontends, gates, and
constants — confirmed as the dominant shape, broader than any single layer.**
Solver dispatch: R43 (paths-aware solve exists in one of four frontends).
Frontends: R28 (no-FR-card handling: CLI silent exit 0 vs GUI/py error),
R46/R63 (plane-wave receive: CLI solves it, three others refuse or silently
zero it), R27 (swept negative-R caveat producer reachable from GUI/py only).
Constants: R55 (junction tolerance `1e-6` duplicated at 12 call sites, no
shared constant, all identical *today*), R54 (`MIN_GPU_RESIDENT_SEGS = 16`
duplicated with no shared provenance in either copy). Gates: R14 (local gate
under-claims what CI covers), R48/R52 (three frequency entry points enforce
three different finiteness domains). This is not a single subsystem's
problem; it is the same authoring habit recurring at every layer of the
project.

**(c) Several gates pass for the wrong reason — confirmed, and worse than the
three named candidates.** The named benchmark-gate-through-a-pipe (R10) and
findings-ledger-literal-prefix (R12) both hold as sabotage-verified. Two more
of the same shape were found beyond the candidates: R11's doc-attachment
checker is blind after the first `#[cfg(test)]` line in a file (three whole
files in the tree are 100% unchecked production code for this reason) and
also masks splices on any of 13 currently-colliding item names; R13's
traceability gate accepts a `VERIFIES:` citation anywhere in *any* source
file — sabotage-verified by moving a real citation into dead production code
and watching `cargo test traceability` still pass. R15's corpus-provenance
script stamps and checks with the *same* naive first-line grep its own
sibling script's docstring names as the textbook false-confidence trap
(latent today, not yet triggered).

**(d) Docs assert capabilities no code provides, and stale trackers point at
closed items — confirmed, and the largest theme by count (9 of 59
findings).** Capability overclaims/underclaims: R01 (README says shipped
features are "pending"), R05 (python-bindings.md says no solver selection
exists; it has since #413), R36 (hosts.toml scheduling fields parsed,
documented as live, read by nothing), R38/R39 (a documented env var and a
`gpu` cargo feature that do nothing). Stale trackers: R03 (roadmap headers
say "(planned)" for phases completed and dated below the header), R04
(PH7-CHK-004 cited as the open tracker for a seam it never delivered — the
seam now has no live tracker at all), R06 (implementation-map/test-catalog/
traceability-matrix all point at a file renamed away two PRs ago), R53
(corpus README's top summary contradicts its own per-case labels further
down). Every instance here is textual and non-destructive, but nine
independent findings of the same shape is a documentation *process* gap, not
nine unrelated typos.

**(e) An additional theme not in the candidate list: degenerate/non-finite
numeric values pass validation at one entry point and are caught (or not) at
another, inconsistently, and the failure mode is a misdiagnosis rather than a
refusal.** R22 (negative multiplicative FR ratio solves silently — the
guard's doc comment asserts a false invariant, magnitude-monotone ≠
sign-monotone), R23 (the worker's `--stdio` path validates the FR *card*
shape, never the frequency value actually solved, so a hand-fed negative
frequency returns a conjugated answer as `status: ok`), R26 (the sweep
truncation validator judges the untruncated request while the expander
truncates it, so one run can warn "only the first 100000 are solved" and then
refuse for a point number that would never run), R48/R52 (`--sweep-config`'s
own ordering checks are all `<= 0.0`, which is false for NaN — a NaN
frequency is accepted, and on a *driven* deck it is misdiagnosed as solver
non-convergence; on a *receive* deck, R48's verifier found it is worse: the
finite-current guard that would catch it never fires because there is no
feedpoint, and NaN reaches exit 0 with a full report of "NaN NaN NaN NaN"
current rows). Five findings, one root cause: no single shared
"is this frequency usable" gate that every entry point calls.

## 5. What the verifiers found that the finders missed

At least five items below were not in the finder's original claim and were
surfaced only during verification:

1. **R63 itself** — spawned by the R46 verifier's own reading of the GUI
   solve path, not by any finder: the GUI's Currents and Pattern tabs solve a
   plane-wave receive deck with an all-zero RHS (`excitation.rs:176,191-196`,
   `linear.rs:674-691`) instead of refusing, producing 51 segments of exactly
   `0.0 mA` and a uniform `-999.99 dBi` pattern floor with no error and no
   caveat.
2. **R59's second, more serious failure mode** — the finder reported only
   that a standard NEC `TL` card is misread with a misleading warning; the
   verifier additionally found that a standard `TL` card *with nonzero shunt
   admittances* is accepted with **no warning at all** and solves to
   materially different physics than intended (`10.914-j21.865` vs the
   `11.992-j21.433` no-TL baseline) — a silent wrong answer from a fully
   valid deck, not just a rejected one.
3. **R57's second divergence** — the finder identified the NRPT-vs-last-tag
   misparse; the verifier additionally proved the `ITGI==0 ⇒ move in place`
   special case is itself non-NEC (NEC keys it on `NRPT==0`), confirmed
   against a second corpus fixture (`dipole-freesp-gm-inplace-shifted.nec`)
   that the verifier discovered already diverges from nec2c (102 vs 51
   segments) for that exact reason.
4. **R06's extra straggler** — the finder cited two stale references to the
   renamed `gpu_kernels.rs`; the verifier found a third,
   `traceability-matrix.md:153`, that the finder missed.
5. **R48's worse path** — the finder's claim was that a NaN frequency gets
   misdiagnosed as solver non-convergence; the verifier, while checking
   whether the finder's quoted diagnostic string was even real (it was — a
   line-wrapped literal a single-line grep missed), separately discovered
   that on a receive-only deck the finite-current guard never fires at all,
   so NaN silently reaches a clean exit-0 report full of `NaN` current
   values, worse than a misdiagnosis.
6. (Bonus, a negative result rather than a finding) **R32's verifier drove 8
   hostile decks** (zero-length wire, zero/negative radius, zero segments,
   1e300 coordinates, radius≫length, coincident wires) looking for the
   "poison task" the finder's severity implied, and **all 8 returned clean
   result lines** — no concrete poison deck exists today; the class remains
   plausible only via OOM/abort, not via validated input.

## 6. Refuted

One finding of the 60 did not survive its verifier.

**R49 — two independent SWR implementations with divergent edge handling.**
*Area:* duplicated numeric producer. *Files:* `apps/nec-gui/src/plot.rs:44`
(`fn swr`, guard `den == 0.0` at :47) and `crates/nec_worker/src/worker.rs:187`
(`fn vswr`, guard `den_sq < 1e-100` at :190).

The finder claimed these two copies were *already divergent* in their
zero-denominator handling, such that the same swept deck could show a finite
SWR in one frontend and an infinite one in another at |Γ| ≈ 1, and framed this
as the house "N copies, one diverged" defect in an incubation stage.

The observations underneath the claim are true and are worth keeping as a
duplication note: both citations are correct, these are the only two SWR
implementations in the workspace, neither lives in a shared crate, and they do
feed two different frontends independently — `apps/nec-cli/src/main.rs` prints
the worker's wire value while `apps/nec-gui/src/sweep_plot.rs:41` calls its own
local `plot::swr`.

**But the load-bearing claim is false.** The verifier modelled both formulas and
swept the boundary directly: the exact `z_re = -z0` point, perturbations down to
1e-400, true IEEE subnormal `den_sq` down to ~1e-320, and 2,000,000 random
`(z_re, z_im)` pairs in [-1e5, 1e5] at z0 = 50. **Zero divergences anywhere**,
including at the exact `den == 0` point, where both return infinity.

The reason is structural rather than incidental, which is what makes the
refutation durable: both functions carry a *later* `gamma >= 1.0` check that
returns `Infinity` whenever the reflection coefficient saturates, and that check
catches every case the differing first guards could possibly separate, because
`num` stays bounded away from zero everywhere the two thresholds disagree. The
two copies are behaviourally identical for every representable input.

Recorded here as refuted rather than quietly dropped, because "these two copies
already disagree" and "these two copies are duplicated but agree" call for
different work: the first is a bug, the second is a consolidation worth doing
only when something else forces the decision — for instance the R44 fix, which
must settle the infinite-VSWR-on-the-wire policy anyway.

## 7. Standing checks earned

Per the audit's own rule — a class found twice earns a mechanical gate, not
an exhortation — here are the classes in this review that clear that bar,
with a concrete, checkable gate for each:

- **Shared frequency-usability gate (closes R22, R23, R26, R48, R52 — five
  independent findings, the single largest earn in this review).** Add one
  function (`is_finite() && sign/range-correct`) in `nec_solver::validate`
  that every frequency entry point — FR-card expansion, `--sweep-config`
  range mode, `--sweep-config` `points_mhz`, and the worker's wire
  `frequency_hz` — must call before solving. Add a test with a planted
  negative-multiplicative-FR, a NaN sweep-config point, and a hand-fed
  negative worker frequency, each asserting refusal, not just success on the
  happy path.
- **Cross-frontend parity test harness (closes R43, R50, R57 as a class, and
  would have caught R24, R28, R46/R63 as siblings).** One test that runs the
  same deck (start with a bent/split geometry, an `EX 4`-over-ground deck,
  and a `GM`-replicated deck) through CLI, GUI (headless solve path), `fnec_py`,
  and the worker, and asserts either identical Z or an explicit, shared
  refusal — never a silent divergent answer. This is the single highest-
  leverage gate in the report because it is the project's own named dominant
  defect class (theme b) made mechanically checkable instead of advised.
- **Named, shared constants for cross-cutting numeric decisions (closes R54,
  R55).** A `JUNCTION_TOL` constant in `nec_model` or `nec_solver`, imported
  at all 12 current call sites, and a single `MIN_GPU_RESIDENT_SEGS` shared
  between `nec-cli` and `nec_worker`. A grep-based CI lint that fails on a
  bare `1e-6` literal outside the constant's own definition would make a
  future re-divergence a build failure instead of a silent drift.
- **Sabotage self-tests for the docs-contract scripts (closes R10, R11, R12,
  R13, R15 as a class — five gates, all shown fail-open by a planted case).**
  Each of these checkers was verified by planting a known-bad input and
  watching it pass; commit that planted case as a permanent negative-control
  test in the same suite (measurement-integrity's own standing
  recommendation), not just as a one-time verification run. Concretely:
  `check-doc-attachment.py` needs a fixture with `#[cfg(test)]` before
  production code; `check-findings-ledger.py` needs a no-space-after-pipe
  row; the traceability gate needs a `VERIFIES:` citation outside any test;
  the benchmark workflow needs `pipefail` (or an explicit exit-code file) so
  `tee`'s exit status is never read through the pipe.
- **A single input-size cap for geometry/grid expansion (closes R09, R17,
  R18, R19, R20, R21, R52 — seven findings, one root cause).** One
  `MAX_ELEMENTS`-style guard, checked once at the point where any of these
  quantities is about to multiply into an allocation size (segment count,
  `GR` repeat count, RP `n_theta*n_phi`, NE/NH `nx*ny*nz`, `--sweep-config`
  range/point counts, worker stdin line length), mirroring the `MAX_FR_POINTS`
  pattern that already exists for the FR axis. A single shared function
  beats seven separate patches because the next new grid-shaped input
  inherits the cap automatically.

**What does NOT warrant a mechanical gate, and why:**

- **R33 (blocking file dialogs in `update()`)** — every trigger is a
  user-initiated modal (open/save/export) during which the UI being blocked
  is expected and harmless; there is no wrong output, and no documented
  responsiveness convention exists to check against. An exhortation ("move
  new blocking calls off-thread") is honest here because there is no
  mechanically distinguishable "bad" case — the existing correctly-async
  block at `main.rs:338-353` is the pattern to copy, not a rule to enforce.
- **R40/R41/R42 (three separate dead pub-API items)** — this is a real
  recurring shape (found three times), but each instance is a single unused
  item with no live caller anywhere, not a construct that can silently
  reappear with different behavior each time. A one-time `cargo` dead-code
  sweep (or `cargo-udeps`) closes today's instances; a standing gate here
  would mostly flag legitimate future API surface added ahead of its first
  caller, which is a worse false-positive rate than the defect it prevents.
- **R60 (pulse-mode RHS sign/scale) and R62 (buried-wire refusal)** — both
  are, on the verifier's own reading, deliberate documented design choices
  (an experimental non-default mode with a loud banner; a tracked non-goal
  with a locked regression case), not defects a gate should prevent from
  recurring. The honest fix for R60 is to either remove the extra `1/λ`
  factor or document the exemption next to the negative-R caveat rule it
  currently violates in silence — a one-time decision, not a check.
- **R14 (check-all.sh under-claims CI coverage)** — fail-closed: CI still
  enforces everything the local script skips, so nothing ships un-gated. The
  fix is a documentation correction (rename the header to match scope, or add
  the missing checks), not a new check on a check.
